# 架构设计决策

本文档只记录长期稳定的架构选择及其理由。当前开发规则、项目状态和具体 API 以根目录 `AGENTS.md` 与源码为准；本文档不保存阶段性进度、旧错误码或历史方法清单。

## ADR-001：领域本体只存一份，其它结构使用稳定标识引用

状态：Accepted

决策：学生、宿舍、宿舍楼本体分别只由 `studentmanager`、`dormmanager`、`buildingmanager` 持有。宿舍床位只保存学生学号，不保存 `student` 对象副本；跨刷新和跨界面操作保存稳定 ID 或复合键，用时重新查询本体。

理由：如果宿舍同时保存学生对象副本，学生资料和住宿状态会形成多个事实源，任何修改都必须同步多份对象。使用学号引用可消除副本一致性问题，也能避免长期保存容器内部指针导致的失效风险。

后果与约束：床位占用以 `dorm.beds` 为事实源，学生位置字段是由 `school` 同步的住宿快照。任何调用者不得重新引入学生对象副本或长期持有 manager 返回的本体指针。

## ADR-002：school 是唯一跨聚合事务边界

状态：Accepted

决策：三个 manager 只管理自己持有的同类本体，不直接调用同级 manager。凡同时修改两个及以上聚合的业务，均由顶层 `school` 统一协调。

理由：让 manager 互相调用会形成依赖环，并把两端同步、失败恢复和错误码分散到多个位置。集中到 `school` 后，可以在一个边界内完成前置校验、具体写入、双向一致性核对、快照恢复和自动保存。

后果与约束：manager 的跨聚合敏感写接口使用 `private + friend class school` 收口。UI、辅助服务和普通调用者只能通过 `school` 执行业务，不得分别修改宿舍床位和学生位置字段。

## ADR-003：按访问需求选择 QHash 与 QMap

状态：Accepted

决策：`studentmanager` 使用 `QHash<int, student>`；`dormmanager` 和 `buildingmanager` 使用 `QMap`。

理由：学生主要按学号定位，没有天然顺序要求，QHash适合高频键查询。宿舍和宿舍楼需要稳定的楼号、宿舍号升序目录，QMap可直接提供有序遍历，并且插入新元素不会使其它元素的引用失效。这种不对称是根据真实访问模式作出的选择。

后果与约束：QHash增删或rehash后内部指针可能失效，学生指针只能就地使用。QMap删除被指向对象后对应指针仍会失效，因此所有长期引用都应保存 ID。

## ADR-004：宿舍床位使用定长整数向量

状态：Accepted

决策：`dorm::beds` 使用定长 `QVector<int>`，下标为床位号减一，值为学生学号，`0` 表示空床，长度恒等于 `max_num`。

理由：该模型可以通过 `bed_id - 1` 直接定位床位，避免遍历和对象副本；空床、住客和最大容量也可以由同一结构表达。

后果与约束：修改最大床位数时必须同步调整向量长度；如果缩容会丢弃已有住客，操作必须拒绝。所有床位号都必须先按当前容量校验。

## ADR-005：宿舍使用复合主键，楼层由宿舍号派生

状态：Accepted

决策：宿舍使用 `(building_id, dorm_id)` 作为复合主键。宿舍号末两位表示房间号，百位及以上表示楼层，`floor = dorm_id / 100`；`dorm` 不再独立保存楼层字段。

理由：不同宿舍楼可以拥有相同宿舍号，因此必须结合楼号定位。楼层可以从宿舍号无歧义计算，继续保存独立字段会产生重复状态和不一致可能。

后果与约束：`student.floor` 只作为入住时同步的位置快照。新增宿舍必须同时校验宿舍号格式、派生楼层和所在楼最大楼层。

## ADR-006：公开查询只读，写入入口受控

状态：Accepted

决策：manager 的公开 `get()` 只返回 const 指针；已入库对象的主键、住宿位置、房间性别和楼属性等敏感字段只能通过 manager 或 `school` 的受控接口修改。

理由：如果外部可以直接修改学生位置，可能出现学生“自称”住在某处、床位却没有记录的僵尸状态；如果外部可以任意修改房间性别，可能在男生楼中产生女舍等永远无法正常使用的“死间”。

后果与约束：公开 setter 只保留对象入库前的必要构造能力。涉及既有引用或其它聚合约束的修改必须由 `school` 完成一致性校验和失败恢复。

## ADR-007：性别约束分为学生、楼栋和房间三层

状态：Accepted

决策：学生性别使用 `0/1/2`，楼栋适用性别使用 `1/2/3`，房间性别锁使用 `0/1/2`。入住时同时检查楼级接纳规则和房间性别锁；未锁定空房由首位住客性别自动锁定。

理由：男女混住宿舍楼需要由房间继续区分男舍和女舍，仅保存楼级性别无法表达这一需求；同时保留未锁定空房可用于验证首位学生入住后的自动占用规则。

后果与约束：前端手工新增学生不允许性别未设置。修改已入住学生性别、楼栋适用性别或房间性别锁时，必须由 `school` 核对现有住客和目标约束。

## ADR-008：复杂业务和文件保存均采用事务式失败恢复

状态：Accepted

决策：存在天然逆操作的局部变更优先执行反向恢复；多对象、多步骤或跨聚合业务在修改前保存必要快照。所有公开写业务完成后由 `school` 在最外层事务中自动保存完整领域快照。

理由：只修改部分对象会破坏学生位置与宿舍床位的双向一致性；业务成功但文件保存失败同样会造成用户看到的数据与重启后数据不一致。

后果与约束：保存失败必须恢复操作前内存快照；恢复不完整时进入只读安全模式。`schoolstorage` 只负责版本化 JSON 校验、备份与原子文件写入，不得成为与 `school` 并列的业务层。

## ADR-009：前端长内容使用 Model/View，不依靠整页滚动补救布局

状态：Accepted

决策：床位和批量预览等可增长内容使用 `QAbstractItemModel + QTableView` 展示；主页面保持固定任务布局，只允许表格、列表等局部内容区滚动。

理由：为每个床位创建独立控件会增加内存占用，并可能把页面高度撑长，破坏16:9窗口布局。Model/View只为可见内容提供展示数据，更适合大容量宿舍和批量结果。

后果与约束：页面不得使用整页 `QScrollArea` 掩盖布局问题。窗口模式重点适配16:9，全屏兼容16:10，新增空间交给表格、列表和任务内容区。

## 较小但长期有效的决定

- 默认构造统一使用 `0` 或空字符串表达“未设置”，使未完整初始化的对象无法被误当成合法本体入库或入住。
- 清空住客并保留房间性别锁与清空住客并解除性别锁使用两个明确命名的函数，不使用难以辨认业务意图的布尔参数。
- UI不长期保存领域对象指针，只保存稳定 ID 或复合键；页面刷新、弹窗返回和业务执行前重新查询本体。
